## 1. Overview

The database consists of **21 data tables** plus the EF Core metadata table
`__EFMigrationsHistory`. All tables live in the `public` schema and use unquoted
`snake_case` names and columns.

**Important:** The database does **not** use native PostgreSQL `ENUM` types or
PostgreSQL `CHECK` constraints for domain values. All status/type/role fields are
stored as `character varying` and validated **in the application layer** via the
C# enums in `backend/Models/Enums.cs`. The only database-level validation is
`NOT NULL` (enforced by EF Core's generated `2200_*_not_null` CHECK constraints
plus the underlying NOT NULL column attribute).

As a result, it is possible for a value that is not in the application enum to
exist in the data. For example, live data contains `employee_unavailability.unavailability_type = 'SickLeave'`
while the C# enum defines `MedicalLeave`, and `email_queue.status` contains
`PermanentlyFailed` which is not in `QueueStatus`. These are documented in
[§25 Enums](#25-enums).

## 3. Table: `users`

### Purpose
Authentication accounts. A user links to at most one `employees` row (staff roles)
or one `visitors` row (Visitor role) via `employee_id` / `visitor_id`.

### Columns

| Column | Type | Nullable | Default | Description |
|--------|------|----------|---------|-------------|
| `id` | `integer` | NO | identity | Unique user identifier |
| `full_name` | `varchar(100)` | NO | — | Display name |
| `email` | `varchar(100)` | NO | — | Login email (unique) |
| `password_hash` | `varchar(255)` | NO | — | BCrypt hash — never plain text |
| `role` | `varchar(50)` | NO | — | App-level role (see [Enums](#25-enums)) |
| `is_active` | `boolean` | NO | — | Inactive users cannot log in |
| `last_login` | `timestamptz` | YES | — | Last successful login |
| `employee_id` | `integer` | YES | — | Linked employee (staff roles) |
| `visitor_id` | `integer` | YES | — | Linked visitor (Visitor role) |
| `created_at` | `timestamptz` | NO | — | Account creation time |
| `updated_at` | `timestamptz` | YES | — | Last update time |

### Keys & Indexes
- **PK:** `PK_users` on `id`
- **Unique:** `IX_users_email` on `email`
- **Unique (partial):** `IX_users_employee_id` on `employee_id` WHERE `employee_id IS NOT NULL`
- **Unique (partial):** `IX_users_visitor_id` on `visitor_id` WHERE `visitor_id IS NOT NULL`
- **FK:** `FK_users_visitors_visitor_id` → `visitors(id)`, ON DELETE NO ACTION

### Notes
- No direct FK exists to `employees`; the employee ↔ user link is enforced in
  application code, and `employees.user_id` carries the reverse link.
- Roles observed in live data: `Admin, CEO, DepartmentHead, Employee, Receptionist, Security, Visitor`.

## 27. Constraint Summary

| Type | Count |
|------|-------|
| PRIMARY KEY | 22 (21 tables + `__EFMigrationsHistory`) |
| FOREIGN KEY | 36 |
| UNIQUE | 10 (3 of them partial/filtered) |
| NOT NULL CHECK (`2200_*_not_null`) | 212 (EF-generated redundant checks) |

### Key Design Decisions
1. **ON DELETE RESTRICT** protects critical business history: visitors and
   employees with visits/appointments cannot be deleted.
2. **ON DELETE CASCADE** is used for dependent child data (appointment properties,
   comments, attachments, reschedules, notifications, schedules, items) and for
   security tokens (`refresh_tokens`).
3. **ON DELETE SET NULL** keeps referencing rows when an appointment or property
   is removed: `visits.appointment_id`, `notifications.appointment_id`,
   `reschedule_requests.responded_by_user_id`, `checkout_items.appointment_property_id`.
4. **No native enums / CHECK constraints**: all domain values are validated in
   the C# application layer, not the database. This is deliberate (simpler EF
   migrations) but allows out-of-enum values to slip in (see `SickLeave`,
   `PermanentlyFailed`).
5. **`GENERATED BY DEFAULT AS IDENTITY`** (not ALWAYS) lets seed scripts insert
   explicit IDs.
6. **Timestamp columns use `timestamptz`** consistently; appointment start/end
   times are full timestamps even though only the time portion is used.
